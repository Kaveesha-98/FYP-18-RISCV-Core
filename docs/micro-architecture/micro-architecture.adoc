#### Possible Performace Issue
* We wait for whole cacheline to be fetched before a stalled instruction can be commited, this obviously increases the latency of the instruction

#### `resultsFromDCache`

##### Updating rules

[cols="1,2", options="header", cols="<,<"]
|===
| Field values | Rule

| `valid === False.B` | 
No instruction should be present on `stalledResultsFromDCache`. 

`resultsFromDCache := cacheLookUpResult`

when `(resultsFromDCache.valid === False.B)`, `cacheLookUpResult` should only depend on `waitOnCacheRead`. How `cacheLookUpResult` is updated will be explained later.
| `(valid === True.B) && (instructionType === noMemoryOperation)` | 
when `(resultsToCommit.fired === True.B)`, `resultsFromDCache := cacheLookUpResult`. Otherwise not updated
| `(valid === True.B) && (instructionType === write)` | 
when `(resultsToCommit.fired === True.B)`, `resultsFromDCache := cacheLookUpResult`. Otherwise not updated

On a cache miss for write instructions, we follow write-through policy. Hence, no need to wait for cacheline to be fetched.

when `(resultsToCommit.fired === True.B)`, assume the write data will be transfered to appropriate write handler.
| `(valid === True.B) && (instructionType === read) && (missState === hit)` | 
when `(resultsToCommit.fired === True.B)`, `resultsFromDCache := cacheLookUpResult`. Otherwise not updated

`(resultsToCommit.fired === True.B) => ((missState === hit) \|\| instructionType === write)`
| `(valid === True.B) && (missState === miss)` | 
when `(fetchRequest.fired === True.B)`, `resultsFromDCache.missState := handlingMiss`. Otherwise not updated. No other fields are updated

When a cache-miss is recevied, we request the cacheline through `fetchRequest` interface.

`(missState === miss) => (instructionType ∈ {atomicRead, read, write})`

When an atomic instruction is a miss, we break the instruction to `atmoicRead` and `atomicWrite` to handle the miss. The `atmoicRead` part will be moved to this register and the miss will be handled like a normal read.

Data is not fetched on a cache-miss of a write instruction.
| `(valid === True.B) && (missState === handlingMiss)` | 
when `(cacheWrite.valid === True.B) && (cacheWrite.bits.address(XLEN-1,3) === resultsFromDCache.bits.instruction.address(XLEN-1,3))`, `dataToRegisterFile` is updated with read data in proper justification and sign extension derived from `cacheWrite.data`. 

`(missState === handlingMiss) => (instructionType ∈ {atomicRead, read})`

In this state we are waiting for the corresponding cache line to fill the cache. Hence:
`(cacheWrite.valid === True.B) => (missState === handlingMiss)`

When `(cacheWrite.valid === True.B) && (cacheWrite.last === True.B)`, then `missState := hit`.

No other fields are updated.
| `(valid === True.B) && (instructionType === atomic)` | 
when `(resultsToCommit.fired === True.B)`, `resultsFromDCache := cacheLookUpResult`. Otherwise not updated.

`(instructionType === atomic) => (missState === hit)`

How we handle miss for atmoic instructions are different from how we handle others
|===
_No other field combinations are possible_

#### `stalledResultsFromDCache`

Used to handle stalls on `resultsToCommit` interface.

`stalledResultsFromDCache.valid => resultsFromDCache.valid`

##### Updating rules

[cols="1,2", options="header", cols="<,<"]
|===
| Field values | Rule
| `valid === False.B` a| 
When one or more of the following conditions are met in the current cycle, bit will be updated according to the instruction present in `waitOnCacheRead` register.

* `resultsToCommit` interface is stalled, (i.e. `resultsToCommit.ready && !resultsToCommit.fired`)
** `stalledResultFromDCache := cacheLookUpResult`
* An atomic instruction is a cache-miss, (i.e. `waitOnCacheRead.instructionType === atmoic && cacheLookUpResult.miss === miss`)
** `stalledResultFromDCache := cacheLookUpResult`
** `instructionType := atomicWrite`
| `(valid === True.B) && (resultsFromDCache.missState === handlingMiss) && (getTagsIndex(cacheWrite.bits.address) === getTagsIndex(stalledResultsFromDCache.bits.instruction.address))` a| 
when `(cacheWrite.valid === True.B) && (cacheWrite.bits.address(XLEN-1,3) === stalledResultsFromDCache.bits.instruction.address(XLEN-1,3))`, `dataToRegisterFile` is updated with read data in proper justification and sign extension derived from `cacheWrite.data`. 

In this state we are waiting for the corresponding cache line to fill the cache according fetch Request created by the instruction in `resultFromDCache`. Hence:

When cache line tag of the target address of both instructions in stalledResultFromDCache and resultFromDCache, the data for the instruction:

1. Can be received through `cache`, in which case, data will not arrive through `cacheWrite` interface while the instruction is in this register
2. Can be received through `cacheWrite` interface, as stated above `dataToRegisterFile` have to be updated correspondigly.

When `(cacheWrite.valid === True.B) && (cacheWrite.last === True.B) && ((getTagsIndex(cacheWrite.bits.address) === getTagsIndex(stalledResultsFromDCache.bits.instruction.address)))`, then `missState := hit`.

`(getTagsIndex(cacheWrite.bits.address) === getTagsIndex(stalledResultsFromDCache.bits.instruction.address)) => ((resultsFromDCache.missState === hit) => (stalledResultsFromDCache.missState === hit))`

| `(valid === True.B) && (resultsToCommit.fired)` |
When `(instructionType === atomic) && (missState === miss)`, `instructionType := atomicWrite`. Otherwise valid := False.B

No other fields are updated.
|===
_No other field combinations are possible_
